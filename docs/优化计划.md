# AskOnce 优化计划（设计与体验）

> 顺序：**定位 → 操作链条 → 页面骨架 → 视觉系统 → 验收**。
> 视觉的「调性」在骨架阶段就定（不推翻现有米色纸感 + 宋体标题 + 砖红），像素级打磨放最后。
> 任何改动都要过一条基准线：**录入一张卡 ≤ 10 秒**。

## 一、方向（四句话）

1. **把主链路补成闭环**：现在的链条在「记下来」和「复盘」之间断了两处——待整理的卡没有入口、同一问题复发时系统不提醒。
2. **每页只回答一个问题**：今天该做什么？这张卡下一步做什么？避免一屏五个同权重按钮。
3. **视觉只做系统化，不做换皮**：状态色、按钮层级、表单控件、焦点态、空状态，统一成一套组件；不做深色模式/PWA/前端框架。
4. **每一步可回归、可演示**：每块改完本地跑通、截图对照、提交 git，答辩时能一条线讲下来。

## 二、明确不做

| 不做 | 理由 |
|---|---|
| 换视觉基调 | 米色纸感 + 宋体标题 + 砖红是「学习手账」的气质，和产品匹配，换掉等于重做骨架 |
| 深色模式 | 需要一整套 token 反向映射，收益小于成本，等主线稳定 |
| PWA / 离线 | 纯 HTTP 部署下做不了，答辩里当"下一步"讲即可 |
| 富文本编辑器 | 会让 Markdown / Anki 导出、XSS 清洗全部失控；图片一律走附件 |
| 向量检索 | 几百张卡的规模，归一化 + 子串 + 词重合已够，且可解释 |

## 四、节奏

| 阶段 | 产出 | 检查点 |
|---|---|---|
| 每块开始 | 说明要改哪些文件、为什么 | 你确认（如无异议直接改） |
| 每块结束 | 本地回归 + 截图 | `git commit` → `git push`，并给你"验证清单" |

部署统一放到最后：本地验证通过后，我给出服务器上传 + 重启 + 校验的命令清单，由你在服务器执行。

## 五、风险与对策

| 风险 | 对策 |
|---|---|
| 粘贴即上传产生"孤儿图"（填一半取消） | 缩略图上直接 × 删除；编辑页与详情页都能看到并清理 |
| 合并卡片是数据操作 | 二次确认弹窗写清后果（删新卡、旧卡复发 +1、截图搬走） |
| 本地环境与服务器不一致 | 本地用同一份 schema.sql；临时 MySQL 独立端口，不碰机器上的 MySQL80 |
| 中途改坏样式 | 每块单独提交，可 `git revert` 回滚 |

## 六、v1.1 升级（截图归属 + AI 参考）

新库直接用 `sql/schema.sql`；**已有数据的服务器**要额外执行一次：

```bash
mariadb -uroot -p askonce < sql/migrate-v1.1.sql
```

新增两处：

- `artifacts.field`：截图属于哪个输入框（`q_what` / `q_why` / `q_how` / `error_text` / `final_solution` …），没有字段的老图仍然归到「截图与链接」；
- `problems.ai_what / ai_why / ai_how / ai_model / ai_generated_at`：AI 参考答案独立存放，**永不写回 `q_*`**。

回退语句写在迁移文件末尾。
